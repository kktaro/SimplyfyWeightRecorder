# ドメインドキュメント

エンジニアリング系スキルがコードベースを調査する際に、このリポジトリのドメインドキュメントをどう読むかを定める。

## 調査の前に読むもの

- リポジトリ直下の **`GLOSSARY.md`**
- **`docs/adr/`**: これから作業する領域に関係する ADR を読む。

これらのファイルが存在しない場合は **何も言わずに進める**。存在しないことを指摘したり、事前に作成を提案したりしない。`/domain-modeling` スキル（`/grill-with-docs` や `/improve-codebase-architecture` から呼ばれる）が、用語や決定が実際に確定した時点で必要に応じて作成する。

## ファイル構成

このリポジトリは single-context 構成とする。

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-xxxx.md
│   └── 0002-yyyy.md
└── app/
```

## glossary の語彙を使う

出力（issue タイトル、リファクタ提案、仮説、テスト名など）でドメイン概念に名前を付けるときは、`GLOSSARY.md` で定義された用語を使う。glossary が避けるよう明記している同義語に流れない。

必要な概念が glossary にまだない場合、それはシグナルである。プロジェクトで使っていない言葉を作り出しているか（再考する）、本当に欠けているか（`/domain-modeling` 向けにメモする）のどちらかだ。

## ADR との矛盾を明示する

出力が既存の ADR と矛盾する場合は、黙って上書きせず明示する。
